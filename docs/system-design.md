# Go版のシステム設計

## 目的と範囲

X API v2から認証ユーザーのブックマークといいねを取得し、SQLiteに保存して分析用に出力する。
Xへの投稿、いいね、ブックマークの追加や削除は行わない。
Deno版のDBとは別のDBを使い、データ移行は行わない。

## データと日時

`posts` は投稿IDごとに本文とAPI応答を保持する。
`relations` は投稿と `bookmark` または `like` の関係を保持する。
同じ投稿が両方に存在しても投稿本体は一件である。
`discovered_at` はその関係の初回発見日時、`last_seen_at` は最後に確認した日時であり、投稿の `fetched_at` はAPIから取得した日時である。
Xから操作日時は取得できないため、出力の `operated_at` は `null` とする。

`users`、`media`、`post_media`、`refs` は著者、メディア、投稿とメディアの多対多関係、参照関係を保存する。
ユーザーとメディアのAPI応答も保持する。
設定とDBはDeno版とは異なるパスに置き、未知の形式の既存DBを拒否する。
DBの新規作成は `db init` で明示する。同期・参照・処理完了の各コマンドは、ファイルがなければ停止する。
既存DBはSQLiteの `mode=rw` で開き、確認後にファイルが消えても新規作成しない。
版の記録が1行で整数の1であること、必要なテーブル・列・キー・索引を検査し、不足を自動修復しない。
`db check` ではSQLiteの `quick_check` と `foreign_key_check` も行う。
全データを走査する検査は明示的なコマンドに限り、投稿ごとの `complete` など通常の起動では繰り返さない。
これらの検査は全CHECK制約の定義や、保存されたアカウントの正しさまで保証するものではない。
DBは最初に同期した認証ユーザーIDに紐付け、別のアカウントの保存関係を混在させない。

## 同期

初回同期と明示された全件同期は既知の投稿では停止しない。
通常の初回同期は、直近のブックマーク100件・いいね50件を保存して増分同期の基準を確定する。
これは選択した範囲の完了であり、全履歴の取得完了ではない。
`initial_limit` で止まる場合は `FinishKind(full=false)` を使い、範囲外の保存関係を未確認にしない。
増分同期は種類ごとに、最後に正常終了した同期より前に発見済みの保存関係を基準とし、既知の関係が連続した時点で停止する。既定の閾値は1件とする。
停止判断はページ内で保持し、後続の新規項目で取り消さない。
失敗した実行で初めて発見した関係は、その後の増分境界として扱わない。
取得したページ全体を一つのトランザクションで保存する。

ブックマークのページサイズは1〜100、いいねは5〜100とし、既定値は5とする。
ページ内の全件が返却対象となるため、小さいページは境界を越えて取得する件数を減らせる。
一方で既知の関係による早期停止は、並び順が変化した場合の完全性を保証しない。
全ページを正常に取得した場合のみ、その種類の一覧に現れなかった関係を未確認とする。

未完了の同期は `sync_resume` に記録し、次回はAPI一覧の先頭から再開する。
期限切れの可能性があるページングトークンを永続的な境界として扱わない。
この再取得には追加料金が発生しうる。
`--max-new` はページの途中でデータを捨てないため、指定値を一ページ分超える場合がある。
初回の制限は新規挿入件数ではなく返却件数で判断し、最後のページの要求件数を残りに合わせる。
いいねの最小要求件数は5件のため、初回の任意の件数制限を最大4件超える場合がある。
各種類のページ数は既定で20ページまでとし、`--max-pages 0` で制限を外せる。
ページ数または新規件数の上限で止まった場合は増分の基準を更新しない。
次回は先頭から再開するため、同じ上限では進まない場合がある。上限を増やすか外して完了させる。
`--full` は初回件数と既知の境界を無視するが、ページ数の上限には従う。
中断した全件同期は、次回の通常同期でも全件同期を続ける。
同期結果の `history_complete` は、その実行が末尾まで確認できた場合だけtrueとなる。
既存DBの完了済み基準と保存データは変更しない。スキーマはv1のままとする。

## 引用とメディア

引用先を `quote_queue` に保存し、深さの小さい順に探索する。
探索は既定で1階層、`--quote-depth` で0〜3階層を選べる。
それより深い引用もキューに保持するが、その実行ではLookupしない。
キャッシュに本文がある場合はLookupせず、未取得分は既定で最大5件ずつ取得する。
Lookupの一要求の最大件数は1〜100件に設定できる。
一回の同期で未取得の引用をLookupする件数は既定で50件とする。
`--max-quote-lookups 0` で制限を外せる。保存済みの引用はこの件数を消費しない。
既定のLookupでは著者・メディアを展開せず、`--metadata` または `--media` の指定時だけ展開する。
深さで除外した引用と未指定のメタデータ補完は先送りとして表示し、実行対象の未完了とは区別する。
同じIDは統合し、循環参照があっても深さを超えて探索しない。
一時障害、アクセス不可、取得不能を記録する。
APIのnot foundだけでは削除を確認できないため、取得不能として扱う。

`--media` はメタデータの補完を有効にし、Xのメディアホストから利用可能なメディアをダウンロードする。
ファイルの保存先とメディアの関係はSQLiteに保持する。
外部投稿やメディアは信頼できない入力である。

## API利用料の記録

一覧ページでは著者とメディアを展開せず、既知の投稿に対する追加リソースの取得を避ける。
新しい投稿の著者とメディアは永続キューに入れる。
既定では補完を省き、`--metadata` または `--media` の指定時だけ、引用の処理後に投稿Lookupで取得する。
既定の補完件数は一回の同期で50件、`--max-metadata-lookups 0` は無制限とする。
すでにキャッシュに著者とすべてのメディアがそろっていれば、各バッチの前に補完キューから除いて再Lookupを避ける。
引用は同じ深さで未試行を優先し、補完キューも未試行を優先する。
失敗済み項目が上限を超える場合は、固定順の再試行が先頭に偏るため、必要に応じて件数上限を増やす。
幅優先のため、浅い引用の失敗が続くと深い引用の未試行項目も待つ場合がある。
メタデータの応答で一部の投稿が返らなくても、他のバッチは件数制限内で続け、欠落のエラーをまとめて返す。
Lookupでは最大件数、投稿単価、著者の最大件数、投稿あたり最大4件のメディアを使って想定額を予約する。
一覧ページでは最大投稿件数から想定額を予約する。
同じ投稿のOwned ReadsとLookupの重複排除がどのように適用されるかは、実際の請求で確認していない。
取得成功後は返却された投稿、ユーザー、メディアのIDをUTC日と種類ごとに重複排除し、推定額を更新する。
最後まで受信できたHTTP 4xx/5xxは、公式の非課金ルールに基づきゼロで精算する。UTC日をまたいでも、この失敗応答には追加の予約を作らない。
通信エラー、読み取り失敗、不正な成功応答は、最大想定額の予約を残す。
HTTP 200の部分成功は、返却されたリソースのみ計上する。エラー配列が空またはnullというだけでは、結果がゼロだったと確定しない。
API呼び出しの試行と、返却リソース数、推定額を記録する。

CLIは月額上限を設けず、推定利用額に基づいて同期を停止しない。
同期結果と `stats` はUTCの暦月について、返却されたリソースに基づく推定額と、結果不明のリクエストの最大想定額を別々に示す。
この期間とXの請求サイクルは別物である。
推定には返却数と価格に関する仮定があり、他のクライアントによる利用や税金を含まないため、Xの請求額とは異なる。
Developer Console側で支出上限が設定されている場合はX側で停止することがある。
Owned Readsの単価は、利用者が適用条件を確認して明示し、対応するブックマーク・いいねのURLのIDが認証ユーザーIDと一致する場合にのみ使う。
最初のユーザーID取得後は、会計処理側のIDも更新する。`/2/users/me` と投稿Lookupの割引は公式の対象一覧で確認できないため、通常単価を維持する。
メディア展開の単価は利用者が設定するまで展開を伴う同期を停止する。本文だけの同期は停止しない。
通常の投稿、ユーザー、Owned Readsの公開単価も設定で変更できる。

公式の[料金表](https://docs.x.com/x-api/getting-started/pricing)はリソースごとの課金とUTC日単位の重複排除を説明している。
重複排除には例外がありうる。
展開に含まれるリソースの実際の課金、請求サイクル、料金変更はDeveloper Consoleで確認する。
`current_month.cost_details` は既存の `billable_reads` と `api_requests` を読み、単価別のリソース日数とエンドポイント・HTTPステータス別の内訳を返す。
スキーマの変更や過去の記録の書き換えは行わない。エンドポイントに含まれるユーザーIDは出力で伏せる。
設定変更後も過去の単価で計上した値を保持する。実請求を取得していないことを `actual_usd: null` で示す。
重複排除では同じ種類・ID・UTC日の最初の記録単価を採用している。異なる価格区分にまたがる場合のX側の扱いは未確認と明示する。
実APIの課金テストは実行していない。

## エージェントと出力

JSONスキーマ `2.0.0` はDeno版の `1.1.0` と互換ではない。
`pending` は投稿と処理目的の組み合わせで未完了の項目を取得し、状態は変更しない。
`complete` は処理成功後に完了を記録する。
一つの投稿がいいねとブックマークの両方にあっても、同じ目的では一度だけ処理する。
投稿本文をエージェントへの指示として解釈しない。

## 認証と運用

OAuth 2.0 Authorization Code with PKCEとリフレッシュトークンを使用する。
コールバックのstateを検証し、トークンはローカル設定に保存する。
Unixの設定ファイルは0600とする。
同期の多重実行はOSのファイルロックで防ぐ。
HTTPにはContextとタイムアウトを設定する。通常のAPI読み取りは429と一時的なサーバーエラーを再試行するが、OAuthトークンの更新は自動再送しない。
長い待機が必要な場合はエラーで返し、後の実行に委ねる。

### Public Clientのトークンを手動で取り込む

`config import` は、発行済みのOAuth 2.0ユーザートークンとリフレッシュトークンを保存する。
ネットワーク通信は行わず、実際のスコープ、トークンとアプリの対応、有効性は検証しない。
`--scopes` には発行時に選択した読み取り・オフライン用の範囲を必須とし、`scope_source: "user_selected"` で記録する。
Client Secretを持つ設定は拒否する。トークンの種類は、取り込み対象のBearerとして記録する。
`--expires-at` は発行元の絶対日時を受け取り、省略時は取り込み時刻を保存して次の同期で更新を必須にする。

LinuxとmacOSでは制御端末 `/dev/tty` を開き、二つの入力欄を通じてエコーを無効にする。
トークンの引数・環境変数・標準入力からの読み込みは行わない。
入力の長さを16KiBまでとし、空白・制御文字・非ASCII文字を拒否する。
入力中は短い間隔でキャンセルを確認し、通常の終了・中断では未読入力を破棄して端末を復元する。
SIGKILLと電源断では復元できない。Windowsでは取り込みを実行せず、既存の `config init` を案内する。

設定の読み込みから入力、保存まで共通ロックを保持する。
保存済みのトークンや更新中の状態がある場合は、明示的な `--replace` を必須にする。
同一のリフレッシュトークンの再取り込みを拒否し、更新中の印を古い値で解除しない。
それ以外の過去のトークンまでは検出できないため、新しい認証情報を使う必要がある。
二つの入力と検証が完了するまでは設定に書き込まない。
保存は既存の一時ファイル・fsync・原子的置換を使い、成功後にメモリ上の設定も更新する。
中断時は旧設定を保持する。保存処理中の強制終了では旧ファイルか新ファイルが残るが、電源断後の耐久性は保証しない。
ユーザーIDとOwned Readsの適用確認は解除し、料金設定などは引き継ぐ。

## レビューで追加した保護

`XSTASH_ACCESS_TOKEN` と `XSTASH_REFRESH_TOKEN` は明示的なエラーにし、環境変数で保存済みトークンを上書きしない。
認証済みのClient IDと異なる環境変数も拒否し、アプリ変更は `config init --client-id` で行う。
再認証に成功するとユーザーIDとOwned Readsの適用確認を解除する。
設定の更新と同期は、読み込みから保存まで設定ファイルに対応する共通ロックで直列化する。
このロックはCLIが取得し、ライブラリの呼び出し元にも取得を求める。外部の書き込みまでは制御しない。

設定にはBearerの種類、スコープ、スコープの根拠も保存する。
必要なスコープの不足だけでなく、要求していないスコープが含まれる応答も拒否する。
初回応答でスコープが省略された場合は要求した範囲を記録し、応答で明示された場合とは区別する。
更新時にスコープが省略された場合は既知の範囲を引き継ぐ。
旧設定などで種類や必要なスコープが不明な場合、同期を始める前に再認証を求める。
初回のオフライン認証ではリフレッシュトークンを必須にし、更新応答で省略された場合は以前の値を保持する。

更新は `ready -> pending -> ready` の順に行う。通常状態では `refresh_state` を省略する。
要求前に `refresh_state: "pending"` と開始時刻を保存し、保存できなければ要求を送らない。
成功応答の検証と新しいトークンの保存が完了してから、メモリ上の認証情報も更新する。
応答不明・エラー・不正な認証情報・中断、ファイルを置き換える前の保存失敗では停止状態を残す。
同じプロセスの後続リクエストと、新しいプロセスからの同期・更新も止める。
置き換え後のディレクトリfsyncだけが失敗した場合も、その実行は停止する。
ただし次のプロセスが、停止状態を解除済みの新しいトークンを読む場合がある。この場合も古いトークンは再送しない。
HTTP 429や5xxも含め、成功を確認できない更新は保守的に再認証を求める。
停止状態は正常な `config init`、または新しい認証情報を使う `config import --replace` の保存で解除する。
印の手動削除や古いトークンの復元はしない。

設定の保存は0600の同一ディレクトリ内の一時ファイルを使い、データをfsyncしてから置き換える。
Unixではその後に親ディレクトリもfsyncする。Windowsではディレクトリfsyncを行わない。
X側の更新とローカル保存を原子的にまとめることはできない。
新しいトークンが届かなかった場合や保存できなかった場合の自動復元は実装せず、再送防止を優先する。
実際の電源断、OSをまたぐ動作、Xのトークン再利用規則はオフラインテストの対象外である。
APIとOAuthのHTTPリダイレクトは自動追従しない。

同期の完了フラグは、終了時のDBトランザクションが成功した後に設定する。
重複した投稿IDで既知の連続件数を増やさず、ページ内の重複IDはエラーにする。
投稿を更新した場合は参照とメディアの関係を置き換え、不足する情報を再取得キューへ登録する。
引用の情報を補完する際にも、元の探索深度を維持する。

HTTPリクエストがUTCの日境界をまたいだ場合、開始日の不確実な見積もりを残し、応答日の利用額も計上する。
この保守的な記録は、実際に二重課金されたことを意味しない。
同期ロックを取得した次の実行では、以前の `running` 状態を中断による失敗として更新し、未処理のキューは保持する。
完了時の基準点の更新と再開情報の削除は、同じトランザクションで確定する。
