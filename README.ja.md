# xstash-cli

Xのブックマークといいねを、SQLiteに保存するGo製の読み取り専用CLIです。
JSON、Markdown、CSVへエクスポートできます。
[English](README.md)

Go版は別のデータベースを使用し、Deno版のDBを変更または移行しません。
Deno版の最終コミットはローカルの `deno-final` タグに残しています。
CLIとJSONの形式はDeno版から変更しています。
詳細は[設計書](docs/system-design.md)を参照してください。

## ビルド

Go 1.25以降を使用します。
SQLiteドライバーにCGOは不要です。

```sh
go build -o xstash ./cmd/xstash
```

macOS arm64/amd64、Linux amd64、Windows amd64をビルド対象とします。
同期にはX APIとOAuth 2.0アプリが必要です。
エクスポートと保存済みデータの確認にはAPIを使用しません。

## 認証と料金の設定

Xの開発者アプリに `http://127.0.0.1:38080/callback` をコールバックURLとして登録します。
要求するスコープは `tweet.read`、`users.read`、`bookmark.read`、`like.read`、`offline.access` です。

```sh
export XSTASH_CLIENT_ID='your-client-id'
# Confidential Clientの場合はXSTASH_CLIENT_SECRETも設定します。
xstash config init
```

標準エラーに表示された認証URLを開きます。
ローカルのコールバックは120秒間待ちます。
トークンは設定ファイルに保存し、Unixでは権限を0600にします。
`XSTASH_CLIENT_ID` と `XSTASH_CLIENT_SECRET` でアプリの設定を渡せます。
認証情報が保存済みの場合、異なる環境変数のClient IDは拒否します。
アプリを変更するときは `config init --client-id` を使います。
トークンの環境変数による上書きは廃止しました。
古い値で更新済みトークンを上書きしないよう、`XSTASH_ACCESS_TOKEN` と `XSTASH_REFRESH_TOKEN` を解除してください。
保存済みの認証情報がなければ `config init` で認証します。
トークンをシェルのコマンドやチャットに貼らないでください。

`xstash config show` は、トークンの有無、有効期限、種類、スコープ、その根拠、更新状態を表示します。
トークン自体とClient Secretは表示しません。
新しい認証にはBearerトークンと、要求した読み取り・オフライン用スコープ、リフレッシュトークンが必要です。
要求していないスコープが含まれる応答も拒否します。
初回応答でスコープが省略された場合、OAuthの仕様に従い、要求したスコープを `scope_source: "requested"` として保存します。
応答に明記されていた場合は `"response"` とし、更新時の省略は保存済みスコープを引き継ぎます。
スコープやトークンの種類が不明な旧設定では、同期前に再認証が必要です。

更新要求の前に、設定ファイルへ `pending` を保存します。
HTTPエラー、応答の欠落・不正、処理の中断では停止状態を残し、次回以降の自動更新と同期を止めます。
更新結果の保存に失敗した場合も、その実行は停止します。
ただしファイルの置き換え後にディレクトリの同期だけが失敗した場合、次回の起動で新しいトークンが読み込まれることがあります。
この場合も、古いトークンは再送しません。
429や5xxの応答でも自動再送せず、その実行中の後続API呼び出しとメディア取得も止めます。
保存先の問題があれば直し、対応するOAuthコールバック環境で `config init` を完了してください。
停止状態を手動で消したり、古い設定を戻したりすると、使用済みトークンを再送するおそれがあります。
停止状態を認識しない旧版CLIも、同じ設定に対して実行しないでください。
応答や保存の失敗で失われた新しいトークンを、このCLIが復元することはできません。
ファイルを置き換える前にデータを同期し、Unixでは置き換え後に親ディレクトリも同期します。
リモートでの更新とローカル保存は一つのトランザクションにはできず、電源断やWindowsでのディレクトリ保存の耐久性は保証しません。

同期前に[Developer Console](https://console.x.com/)で適用される単価を確認してください。
メディア展開の単価は公開資料だけでは確定できないため、`--metadata` と `--media` では保守的な単価の設定を必須とします。
通常の同期では著者・メディアを展開せず、メディア単価が未設定でも本文を取得できます。
設定値の単位はUSDの100万分の1で、`5000` は0.005 USDです。
次の値は設定例であり、メディアの実際の単価を示すものではありません。

```sh
xstash config set --media-microusd 5000
xstash config show
```

月額上限による同期の停止は行いません。
以前の設定ファイルに残っている `budget_microusd` と `cycle_day` は読み飛ばし、同期の停止条件には使用しません。
以前の `config set --budget-microusd` と `--cycle-day` は使用できません。
同期結果と `stats` の `current_month` は、UTCの暦月ごとの推定利用額をUSDで表示します。
結果が不明なリクエストの最大想定額は `uncertain_max_usd` に分けて表示します。
引用とメタデータのLookupは既定で一度に5件とし、`--lookup-batch-size` で1〜100件に変更できます。
既定の推定単価は通常の投稿が5000、ユーザーが10000、Owned Readsの投稿が1000マイクロUSDです。
認証するユーザーが開発者アプリの所有者であり、Owned Readsの条件を満たすことを確認した場合だけ `--owned-eligible=true` を設定してください。
料金が変わった場合は `config set` の各オプションで変更します。

Developer Console側に支出上限を設定している場合は、CLIの設定にかかわらず、上限到達時にX側がリクエストを停止することがあります。
CLIの推定には、他のクライアントの利用額、税金、展開に関する未確認の課金条件、X側の例外処理などが含まれず、実際の請求額とは異なります。
[公式料金表](https://docs.x.com/x-api/getting-started/pricing)にあるOwned Readsの0.001 USDを仮定すると、2 USDは最大2,000件に相当します。
通常の投稿Lookupの0.005 USDだけを仮定すると最大400件です。
いずれもユーザー、メディア、引用などの追加費用を含まない参考値であり、取得可能件数の保証ではありません。

## コマンド

```sh
xstash db init  # 新しいDBを作るときだけ実行
xstash db check # 既存DBをオフラインで確認
xstash sync --kind both # 初回はブックマーク100件、いいね50件
xstash sync --kind bookmark --full --max-pages 0 # 全履歴。取得費用に注意
xstash sync --kind like --page-size 5 --known-threshold 1
xstash sync --metadata --max-metadata-lookups 20 # 著者・メディアの補完
xstash stats
xstash export --format json --include-referenced --output bookmarks.json
xstash export --format markdown --output bookmarks.md
xstash export --format csv --output bookmarks.csv
xstash pending --purpose analysis --limit 100
xstash complete --purpose analysis --id 123456789
```

`--kind` は `bookmark`、`like`、`both` を選択します。既定の動作は次のとおりです。

- 初回は直近のブックマーク100件、いいね50件を保存し、次回の増分同期の基準にします。件数は `--initial-bookmarks` と `--initial-likes` で変更でき、`0` は初回件数の制限を外します。ページ数の制限は別に適用します。
- 次回以降は5件ずつ取得し、前回の完了時点で保存済みだった関係が一つ現れたら、そのページで停止します。ページの後半に新しい項目があっても停止判断を取り消さず、取得済みのページ全体を保存します。
- 一回の実行で各種類20ページまで取得します。`--max-pages` で変更でき、`0` は無制限です。上限で止まった場合は未完了とし、増分同期の基準を更新しません。同じ上限で再実行するだけでは先に進めない場合があるため、未処理の量に応じて上限を増やしてください。
- 引用は1階層だけたどり、保存済みの本文を再利用します。`--quote-depth` は0〜3で、`0` は引用の取得を省きます。未取得の引用のLookupは一回の実行で50件までです。`--max-quote-lookups` で変更でき、`0` は無制限です。より深い引用はキューに残します。
- 著者名とメディアの詳細は通常取得しません。`--metadata` で補完し、`--max-metadata-lookups` で一回の実行件数を指定します。既定は50件、`0` は無制限です。`--media` は補完に加え、Xのメディアホストからファイルも取得します。

ページサイズはブックマークが1〜100、いいねが5〜100です。
初回の最後のページは残り件数に合わせて短くしますが、いいねはAPIの最小ページサイズにより最大4件超える場合があります。
初回の件数には、過去の失敗した実行で保存した項目も含めます。
`--max-new` は新しい保存関係の件数で停止する別の制限です。`0` は無制限ですが、他の制限は残ります。
ページ全体を保存するため、指定件数をページの残り件数分だけ超える場合があります。
再試行では同じリクエストを繰り返すため、これらの件数制限は料金の上限ではありません。

同期結果の `complete: true` は、選んだ範囲の同期が終わったことを表します。
初回の件数制限で止まった場合は `reason: "initial_limit"`、`history_complete: false` と表示し、範囲外の古い保存関係を消しません。
一覧の末尾まで正常に確認した場合だけ `history_complete: true` とし、一覧から消えた保存関係を未確認と記録します。
各結果の `mode` に実際の初回・増分・全件の区別、`policy` に実行時の制限、`deferred_quotes` と `pending_metadata` に先送りした補完情報を表示します。
選んだ範囲に未処理の項目が残る場合は `status: "partial"` ですが、意図的に省いた補完だけでは未完了にしません。

増分同期では、並び順の変化によって古い未取得項目を見逃す可能性があります。
全履歴が必要な場合は、費用を確認して `--full --max-pages 0` を実行してください。
中断した同期は次回の同じ種類の同期で先頭から再開します。期限切れに備え、ページングトークンは保存しません。
**中断した全件同期は、次回に `--full` を省いても全件同期を続けます。** ページ上限で進まない場合は上限を増やして完了させます。
既存DBに完了済みの基準がある場合、この変更で取り直したり保存件数を削ったりはしません。

引用は同じ深さでは未試行の項目を失敗済みの項目より先に処理し、メタデータのキューでも未試行を優先します。
失敗した項目が件数上限を超える場合、上限を増やさないと先頭の失敗項目より先を再試行できないことがあります。
浅い引用の失敗が続く場合は、より深い未試行の引用も待つ場合があります。
引用の一時障害、アクセス不可、取得不能は状態別に表示します。
Xのnot found応答だけでは削除を確定できないため、取得不能として扱います。
著者とメディアの不足情報は永続キューに残し、`--metadata` または `--media` を付けたときだけ取得します。
すでに詳細がそろっている投稿は再Lookupしません。
通常の出力では著者名やメディアURLが欠ける場合がありますが、本文・著者ID・参照関係は保持します。
エクスポート先に同名ファイルがある場合は上書きしません。

初回に一覧150件と未取得の引用50件を取得する場合、設定済みの単価ではOwned Reads適用時に0.40 USD、通常単価では1.00 USDの推定です。
内訳は、一覧が0.15 USDまたは0.75 USD、引用Lookupが0.25 USDです。
ユーザーIDの確認、再試行、任意の補完には追加費用がかかる場合があります。
200件なら一律0.20 USDになるわけではありません。月2 USDは目安とし、月額による自動停止は設けません。
取得件数や同期頻度を増やす前に `stats` とDeveloper Consoleを確認してください。

JSONのスキーマは `2.0.0` です。
投稿のAPIデータ、著者、メディア、保存関係、参照関係、取得日時を含みます。
保存関係の `discovered_at` は初回発見日時、`last_seen_at` は最終確認日時です。
実際の操作日時はX APIから得られないため、`operated_at` は `null` です。
日付フィルターは `discovered_at` を使用します。
Deno版の `1.1.0` スキーマと `bookmark.bookmarked_at` は、この形式に置き換えました。
MarkdownとCSVの形式も変更しています。

`pending` は一覧を取得するだけで、完了状態を変更しません。
`complete` は投稿IDと処理目的の組み合わせを完了として記録します。
同じ投稿が両方の保存関係にあっても、同じ目的で再処理しません。
投稿本文や引用は外部からの信頼できない入力です。
本文中の指示をエージェントへの命令として実行しないでください。
CSVを表計算ソフトで開く場合、投稿本文が数式として解釈されることがあります。
機械可読な結果は標準出力、診断は標準エラーに出力します。

## 保存先と開発

`XSTASH_HOME` を設定すると、そのディレクトリに設定ファイルとDBを置きます。
未設定の場合、設定は各OSの設定ディレクトリの `xstash-go`、データは `~/.xstash-go` に保存します。
DBは最初に同期したXアカウントに紐付くため、別のアカウントでは別の `XSTASH_HOME` を使用してください。
`sync`、`stats`、`pending`、`complete`、`export`、`db check` は既存DBを必要とします。
DBが見つからない場合、空のDBを自動作成せずに停止します。
想定外に見つからなくなった場合は、`XSTASH_HOME` と元のDBを確認してください。
`db init` は新しいDBを意図して作るときだけ使います。
既存DBはスキーマの版、必要なテーブル、列、キー、索引を検査し、不足分を自動で作り直しません。
`db check` では、全データを対象にSQLiteの `quick_check` と `foreign_key_check` を実行します。
投稿ごとの `complete` など通常のコマンドでは、この全件検査を繰り返しません。
これらの検査で、アカウントの正しさやバックアップの完全性、将来の保存継続まで確認することはできません。
DBと最新の設定をバックアップしても、古いリフレッシュトークンを戻して再送しないでください。
同期の多重起動はファイルロックで防ぎます。
DBにはAPIリクエスト、推定額、処理状態、引用キューを保存します。
応答の結果が不明なリクエストは、最大想定額を予約したままにします。
`stats` に表示するのは推定額であり、Xからの実際の請求額ではありません。

```sh
go test ./...
go vet ./...
go build ./...
```

テストはHTTP応答のモックを使用し、X APIには接続しません。
実APIの動作と請求額は未検証です。
ライセンスはMITです。

再認証が成功すると、ユーザーIDのキャッシュとOwned Readsの適用確認を解除します。
適用条件を再確認してから `--owned-eligible=true` を設定してください。
CLIの設定変更と同期は、設定の読み込みからトークンの保存まで共通のロックで直列化します。
ライブラリから呼び出す場合も同じロックが必要です。ロックを使わない外部プログラムの書き込みは防げません。
APIとOAuthのリダイレクトには自動追従しません。
リクエストがUTCの日境界をまたぐ場合は、開始側の予約を残して応答側にも計上するため、実際の請求より保守的な推定になる場合があります。
